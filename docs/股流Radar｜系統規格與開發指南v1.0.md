# 股流 Radar｜系統規格與開發指南 v1.0

**文件定位：** 本文件是《股流 Radar》總綱，整合四階段需求訪談結論，並對《Phase 1 PWA 核心產品規格與 Wireframe v0.2》（下稱 P1 規格）做出修訂決議。兩份搭配使用：本文管「系統全貌與執行決定」，P1 規格管「畫面與驗收細節」。

**決策來源：** 2026-09 產品負責人四階段訪談（標的與數據源 → 策略細節 → UX 與通知 → 技術與時程）。

## 1. 北極星與產品原則

> **股流 Radar 先幫你找到台股熱門類別，再用價格行為g研判框架，協助你區分已確認資訊、可能情境與尚需等待的交易條件。**

- 兩段式角色：**雷達**（發現熱區）→ **g研判**（在熱區內用 PA 框架規劃條件）。
- 核心用戶價值：**交易有底**——自選股每天知道「該等什麼條件、錯了在哪裡認錯」，不盲目追高殺低（對應 P1 規格流程 C「避免追高」）。
- 合規原則沿用 P1 規格 §8：條件式語句（若…則…）、三區分（已確認／推測／待等待）、不保證獲利、熱門不等於可交易。

## 3. 系統架構總覽

```text
[資料源] TWSE/TPEx OpenAPI、期交所 TAIFEX、FinMind、mis 盤中快照、（Phase 3+）券商 API
   ↓  供應商抽象層：同一組介面，0 元源 ↔ 收費源可替換，上層程式不動
[數據管線] Phase 1 盤後批次 → Phase 2 盤中輪詢 → Phase 2+ 自選股高頻輪詢
   ↓  儲存：SQLite（可平移 Postgres）
[PA 事實層] 純演算法：結構／關鍵價位／形態／量價 → 結構化 JSON（§4）
   ↓
[g研判引擎] 六段框架（P1 規格 §4 為準）＋ 策略層 Strategy Profiles（§5）＋ marketContext
   ↓  Phase 1 規則引擎＋固定模板（零 AI 成本）→ Phase 2 LLM 只做敘事
[呈現] PWA（熱區／掃描／g研判／自選）＋ [推播] Telegram/LINE（Phase 2）
```

三條架構約束：
1. **資料源可替換**——日後升級即時行情或對外開放，只換抽象層底下的供應商。
2. **事實先於 AI**——任何分析輸出前，事實層必須先跑完；LLM 永遠不計算價位、不發明形態。
3. **單向依賴**——呈現層只讀g研判輸出，g研判只讀事實層，事實層只讀資料庫。

## 4. PA 事實層（Price Action Facts Layer）

### 4.1 白話定義

「事實層」是一支**純程式**，把原始 K 線（開高低收量）先計算成一份**客觀事實清單**；g研判（模板或 AI）**只能引用這份清單，不能自己發明**形態或價位。

範例輸出（台積電日線）：

```json
{
  "symbol": "2330",
  "asOf": "2026-09-05",
  "swings": {
    "lastHigh": { "date": "2026-09-03", "price": 1120 },
    "lastLow":  { "date": "2026-09-05", "price": 1040 }
  },
  "structure": { "trend": "up", "sequence": "HH+HL", "confidence": "medium" },
  "keyLevels": [
    { "type": "支撐區", "range": [1040, 1055], "basis": "6 日密集成交＋前低", "status": "confirmed" }
  ],
  "patterns": [
    { "name": "PinBar", "date": "2026-09-05", "status": "unconfirmed" }
  ],
  "volume": { "todayVs20dAvg": 1.8 }
}
```

### 4.2 為什麼需要（三個理由）

1. **防幻覺**：讓 LLM 直接看原始數字會編故事、每次說法不一致；先給它客觀事實，它只負責解讀與敘事。
2. **強制執行「未確認」**：P1 規格 §4.3「沒有足夠證據時顯示未確認」之所以能被強制執行，是因為形態認定是程式給的、帶 `status` 欄位，不是 AI 嘴上說的。
3. **可重現、可回測、可掃描**：同一組 K 線輸入必須產出完全相同的事實；Phase 2 的策略掃描器不可能每天叫 AI 看全市場——先讓事實層機械過濾，最後才讓 AI 寫敘事。

### 4.3 演算法清單（Phase 1 範圍）

| 模組 | 演算法 | 參數（預設） |
|---|---|---|
| Swing 偵測 | Fractal pivot（左右 N 根確認） | N=3，可調 |
| 結構判定 | Swing 序列 → HH/HL/LH/LL → 上升/下降/震盪＋信心 | 近 60 根為評估窗 |
| 關鍵價位 | 前高前低、密集成交區（量價分布 HVN/LVN）、跳空缺口、整數關卡 | 輸出為「區域」，禁單點假精準 |
| 形態 | Pin Bar（影線比例門檻）、多空吞沒、雙頂/雙底（容差比對）、突破/假突破（收盤確認＋量能）、回踩 | 全部帶 confirmed/unconfirmed |
| 量價 | 今日量 ÷ 20 日均量 | — |

### 4.4 驗收原則

- 同輸入 → 同輸出（100% 可重現，寫單元測試）。
- 「未確認」是常態輸出，不是錯誤狀態。
- 事實層不產生任何建議文字——建議是g研判層的事。

## 5. g研判與多策略模組

### 5.1 三層職責

| 層 | 職責 | 不做什麼 |
|---|---|---|
| PA 事實層 | 算客觀事實（§4） | 不給建議 |
| g研判引擎 | 固定六段框架輸出（P1 規格 §4） | 不跳過三區分 |
| 策略層 | 決定「看什麼、等什麼、什麼算錯」的視角 | 不直接下單指令 |

### 5.2 策略檔（Strategy Profile）資料結構

```ts
interface StrategyProfile {
  id: string;                    // "breakout-pullback"
  name: string;
  scope: "builtin" | "user";     // 內建 / 使用者自訂
  timeframes: Timeframe[];
  filters: Condition[];          // 前置過濾：籌碼／熱區／流動性
  triggers: Condition[];         // 進場觸發：引用 PA 事實欄位
  invalidations: Condition[];    // 失效條件
  riskTemplate: { stopRule: string; target1: string; target2: string; rrMin: number };
  notifyCopy: string;            // 推播文案模板（一律條件式語句）
}
```

`Condition` 只能引用事實層與籌碼欄位，例如：
`structure.trend == "up" && lastEvent == "pullback_to_support" && institutionBuyStreak >= 3`。

### 5.3 內建策略清單（Phase 1 僅 pa_default，其餘 Phase 2 上架）

| id | 名稱 | 邏輯骨架 | 備註 |
|---|---|---|---|
| `pa_default` | 條件式 PA | 純六段框架，無籌碼過濾 | Phase 1 唯一 |
| `breakout-pullback` | 突破回踩 | 前高突破（已確認）→ 等回踩不破 → 信號 K → 進場區＝回踩區；失效＝收盤跌回突破位下 | 熱門股防追高主力策略 |
| `institution-tailwind` | 法人順風 | filter＝法人連買 ≥ 3 日＋所屬熱區為聚焦/升溫；trigger＝支撐區回踩＋吞沒確認 | 籌碼過濾器（訪談 Q4-A） |
| `trend-follow` | 趨勢跟隨 | HL 之上回調做多；失效＝跌破前 HL | — |
| `range-fade` | 箱體邊緣 | 震盪結構＋邊緣反轉 K；區間中間＝不交易 | — |
| `gap-play` 等 | 開盤區間/當沖向 | 需盤中數據 | Phase 3+ |

### 5.4 自選股 × 策略掃描（「交易有底」的實現）

```text
自選股清單（每檔可綁 0~N 個策略，Phase 1 先全域綁 pa_default）
→ 每日盤後批次掃描（Phase 2 增加盤中事件掃描）
→ 條件未滿足 → 「等待狀態」：明列還缺哪些條件
→ 條件滿足 → 候選訊號（經風控與去重）→ 推播「策略條件已符合」＋g研判頁連結
→ g研判頁顯示該策略視角的六段分析
```

推播文案原則沿用 P1 規格 §11：說「策略條件已符合」，不說「現在買進」，並附已確認條件、未確認條件、結構失效位、風險提示。

### 5.5 LLM 的位置（Phase 2 起）

LLM 只做兩件事：**把事實＋策略結果整理成敘事**、**回答使用者追問**。不得計算價位、不得推翻事實層、不得繞過三區分。Phase 1 用規則引擎＋固定模板上線（P1 規格 §9 同此建議），零 AI 成本。

## 6. 熱區與籌碼規格落地

熱度公式（沿用 P1 規格 §3）各成分的資料可得性：

| 成分 | 權重 | 計算式 | 免費源 |
|---|---|---|---|
| 資金流向 | 35% | 類股成分股三大法人買賣超合計（近 5 日） | TWSE T86 / FinMind，自行聚合 |
| 價格強度 | 25% | 類股市值加權漲幅（5 日/20 日） | 自算 |
| 成交量異常 | 20% | 類股總成交值 ÷ 20 日均 | 自算 |
| 上漲廣度 | 20% | 成分股上漲家數占比 | 自算 |

- **產業分類**：TWSE 上市櫃產業別為基礎；「AI 伺服器」等自訂主題類別以人工對照表維護（Phase 1 先少量手建，Phase 2 做管理介面）。
- **marketContext（進g研判卡）**：所屬熱區分層、個股法人連買/賣超天數、大盤加權指數狀態；Phase 2 加法人近月買超成本區與融資套牢區（對應訪談 Q4-B「籌碼畫上圖」）。

## 8. 技術棧與部署（已代為決定）

| 決定 | 選擇 | 白話理由 |
|---|---|---|
| 語言/框架 | 全 TypeScript：Next.js（PWA）＋ Node 排程 worker | 一套語言包辦畫面、伺服器、資料庫操作，一人維護最省力 |
| 資料庫 | SQLite 起步，量大再平移 Postgres | 0 元、免維運；schema 設計成可搬 |
| 部署 | PWA/API 放免費層雲（Vercel/Fly）；抓取 worker 放台灣網路環境＋雲 DB | 手機隨時開網頁；抓資料用台灣 IP 避限流 |
| LLM | Phase 1 不用（規則引擎＋模板）；Phase 2 免費層 flash 級模型起步 | 零 AI 成本上線，用量可控 |
| 通知 | Phase 2：Telegram Bot 起步；LINE 視訂閱方案再接 | Telegram 免費無上限；LINE 免費額度 200 則/月 |
| 時程 | 沿用 P1 規格 Sprint 1–4，每 Sprint 1–2 週，Phase 1 約 4–8 週 | Sprint 1 用 mock data，第一週末就有畫面可看 |

專案結構建議（單體 repo）：

```text
stockflow-radar/
├── app/               # Next.js PWA（熱區/掃描/g研判/自選）
├── packages/facts/    # PA 事實層（純函式，可單測）
├── packages/pa/    # 六段框架＋策略層
├── workers/pipeline/  # 抓取＋計算排程（台灣環境執行）
└── data/              # SQLite schema ＋ migrations
```

## 10. 風險與合規邊界

- 產品文案邊界：沿用 P1 規格 §8 可提供／不可提供清單。
- 每張分析卡固定顯示 `disclaimer`（P1 規格 §9 已留欄位）。
- 資料授權：免費源授權條款於「對外開放」前逐一檢視——這是開放功能的**前置條件**，不是上線後補件。
- 當沖前置：交易成本（手續費＋證交稅）必須計入 R/R 與停利門檻，避免「小波段假勝」。

## 11. 驗證指標

沿用 P1 規格 §12，另加兩條系統指標：

| 指標 | 目標 |
|---|---:|
| 事實層可重現性（同輸入同輸出） | 100% |
| 策略掃描誤報（條件未滿足卻推播） | 0 |
